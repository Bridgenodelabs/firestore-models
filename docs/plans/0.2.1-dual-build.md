# 0.2.1 — dual ESM/CJS build

Implementation plan for `@bridgenodelabs/firestore-models`. Companion to the Claude Code prompt; save as `docs/plans/0.2.1-dual-build.md`.

**Scope:** packaging only. No API changes, no new runtime dependencies, no source changes beyond what the build requires.

---

## Why

`0.2.0` is `"type": "module"`, ESM-only, with subpaths exposed only through an `exports` map. A TypeScript consumer compiling as CommonJS with `moduleResolution: node10` — which is what an Nx workspace uses for node-targeted projects — cannot import it. **`node10` ignores `exports` maps entirely**, so conditions alone do not reach these consumers.

Observed against a real consumer (PitchEvaluator3 `libs/common`, ts-jest, 401 tests):

| Specifier | Bundler (exports conditions) | node10 + ts-jest |
|---|---|---|
| `@bridgenodelabs/firestore-models` | resolves | loads, but `Object.keys(pkg)` is `['default']` |
| `.../firestore-models/core` | resolves | TS2307 — cannot find module |
| `.../firestore-models/dist/core/index.js` | not exported under conditions | resolves, then `createValidator is not a function` |

Production builds were never the problem — esbuild-based Cloud Function builds succeeded with the library in place. The failure is confined to CommonJS TypeScript resolution.

## Unknowns to resolve before writing code

The plan below assumes a layout. Check it against the repo and adapt:

- Current entrypoints. The plan assumes `.`, `./core`, `./web` (Firebase Web SDK adapter), `./react` (hooks). Confirm the real set.
- Current build tooling and whether it already emits declarations.
- Test runner and whether it runs against `src` or `dist`.
- Whether `src` uses extensionless relative imports — these need `.js` specifiers or a bundler-based build; note which.

## Target: package layout

Recommended: **make CommonJS the default format and ESM the extension-tagged one.** This maximizes node10 compatibility, since node10 stubs then point at ordinary `.js` and `.d.ts` files with no extension-mapping subtleties.

```
package.json          "type": "commonjs"
dist/
  index.js    index.d.ts     index.mjs   index.d.mts
  core/index.js  core/index.d.ts  core/index.mjs  core/index.d.mts
  web/…  react/…
core/package.json     # node10 stub, generated at build time
web/package.json
react/package.json
```

The alternative — keeping `"type": "module"` with `.cjs`/`.d.cts` for the CommonJS build — also works and is fine if you prefer it. It just puts more weight on `.d.cts` being resolved correctly by older TypeScript versions. Pick one, and let the fixtures decide if it's wrong.

### `package.json`

```jsonc
{
  "type": "commonjs",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "module": "./dist/index.mjs",
  "exports": {
    ".": {
      "import": { "types": "./dist/index.d.mts", "default": "./dist/index.mjs" },
      "require": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }
    },
    "./core": {
      "import": { "types": "./dist/core/index.d.mts", "default": "./dist/core/index.mjs" },
      "require": { "types": "./dist/core/index.d.ts", "default": "./dist/core/index.js" }
    },
    // ./web, ./react identically
    "./package.json": "./package.json"
  },
  "typesVersions": {
    "*": {
      "core": ["./dist/core/index.d.ts"],
      "web": ["./dist/web/index.d.ts"],
      "react": ["./dist/react/index.d.ts"]
    }
  },
  "files": ["dist", "core", "web", "react"],
  "sideEffects": false
}
```

Note that `types` must come **first** inside each condition object — conditions are matched in order, and a `default` ahead of `types` swallows it.

### node10 subpath stubs

`typesVersions` fixes types for node10 but not runtime resolution. node10 resolves `@scope/pkg/core` by looking for `core.js`, `core/index.js`, or `core/package.json`'s `main` — so generate a stub directory per subpath:

```jsonc
// core/package.json — generated by the build, committed to .gitignore
{
  "main": "../dist/core/index.js",
  "module": "../dist/core/index.mjs",
  "types": "../dist/core/index.d.ts",
  "sideEffects": false
}
```

Generate these in a postbuild script rather than hand-maintaining them, and make sure they're in `files`.

### Build tool

`tsup` is the least-effort fit (esbuild under the hood, handles dual format, extensions, and declarations):

```ts
export default defineConfig({
  entry: ['src/index.ts', 'src/core/index.ts', 'src/web/index.ts', 'src/react/index.ts'],
  format: ['cjs', 'esm'],
  dts: true,
  sourcemap: true,
  clean: true,
  treeshake: true,
  external: ['firebase', 'firebase-admin', 'react'],
});
```

`unbuild` or two `tsc` passes work equally well. Whatever you choose, **the CommonJS output must carry real named exports.** The `['default']` result in the table above is the signature of ESM transpiled at consume time, not of a CJS artifact — esbuild's CJS output does this correctly, but the fixtures in the next section are what prove it.

## Tests

### Existing suite

Runs unchanged. If the build change requires touching a unit test, stop — that means the API moved, which is out of scope for this release.

### Packaging fixtures — the actual deliverable

Add `test/packaging/`. Every fixture installs the **packed tarball** into a temp directory. Testing against `src`, a workspace link, or `file:..` will pass while the published package remains broken — that is precisely how `0.2.0` shipped.

Harness (`scripts/verify-packaging.mjs`): run `npm pack`, then for each fixture create a temp dir, `npm install <tarball>`, run the fixture's command, assert exit code 0. Fail loudly on any nonzero.

| Fixture | Config | Asserts |
|---|---|---|
| `cjs-require` | plain node, no TS | `require(pkg)` and `require(pkg + '/core')` both expose named exports; `Object.keys()` does **not** equal `['default']`; `typeof createValidator === 'function'` |
| `esm-import` | plain node, `.mjs` | named imports from root and `/core` resolve and are callable |
| `ts-node10-cjs` | `module: commonjs`, `moduleResolution: node10`, ts-jest | **the release-blocking one** — `tsc --noEmit` passes, and a Jest test importing `{ createValidator }` from `/core` defines a model and round-trips a document |
| `ts-node16` | `moduleResolution: node16`, both `module: commonjs` and `module: node16` | types resolve to the matching format under both; no `.d.ts`-masquerading-as-ESM errors |
| `bundler` | `moduleResolution: bundler` + a real esbuild or vite build | build succeeds, output runs |

The `ts-node10-cjs` fixture should mirror the consumer that found the bug: TypeScript, CommonJS, ts-jest, importing the `/core` subpath. Include the original probe as an explicit assertion, since it's the clearest statement of the regression:

```ts
import * as pkg from '@bridgenodelabs/firestore-models';
expect(Object.keys(pkg)).not.toEqual(['default']);
```

### Static checks

```
npx publint --strict
npx @arethetypeswrong/cli --pack
```

Both run against the packed tarball, both gate the release. `attw` catches the masquerading-types class of bug directly; treat any 🚫 as a failure rather than reasoning about whether it matters.

## CI

Extend the existing workflow: build → unit tests → `npm pack` → packaging fixtures → publint → attw. Run the matrix on Node 18, 20, and 22 — node10 resolution behavior is a TypeScript concern rather than a Node one, but the runtime interop assertions are worth checking across versions.

## Acceptance criteria

1. `ts-node10-cjs` fixture passes, including `tsc --noEmit`.
2. All five fixtures green against the packed tarball.
3. `publint --strict` and `attw --pack` clean.
4. Existing unit tests pass with zero modifications.
5. Zero runtime dependencies; the public API is byte-identical to `0.2.0`.
6. No consumer-side workarounds anywhere in the fixtures — no `transformIgnorePatterns`, no `--experimental-vm-modules`, no `extensionsToTreatAsEsm`, no deep `dist/` paths. If a fixture needs one of these to pass, the release isn't done.
